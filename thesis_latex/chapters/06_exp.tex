\section{综合风险分析链路验证}
\subsection{疾病风险建模与训练侧验证}
慢病风险预测模型由 \codeid{ai_core/train_risk_models.py} 训练完成，针对各目标病种独立构建 LightGBM 二分类器。训练阶段采用分层抽样划分训练集与测试集，并通过 \codeid{is_unbalance=True} 处理阳性样本占比较低的问题。与单纯追求分类分数相比，当前训练过程更强调防泄漏控制：脚本在每个病种训练前依据 \codeid{LEAKAGE_MAPPING} 剔除与目标诊断高度重叠的变量，从而避免把诊断同义特征直接作为预测依据。该设置使训练输出更接近真实筛查场景，也保证了在线服务与训练阶段的特征边界保持一致。

\codeid{train_risk_models.py} 当前会直接输出 $AUC$ 与 Accuracy，用于给出训练侧的基础性能反馈；不过就本轮可复核材料而言，更重要的结论并不是某一病种是否取得极高分数，而是训练阶段保存的模型、特征集合与服务侧实际消费的输入保持了一致。与此相对应，行为风险模型和营养视觉模型在当前系统中主要承担辅助修正与扩展输入作用：前者为行为风险修正因子提供支持，后者为饮食与营养记录补充可结构化信息。因此，本章不再将二者作为与临床主模型并列的独立 benchmark，而是将其视作多模态融合链路中的辅助证据来源。

\subsection{多模态融合链路验证}
多模态融合部分的目标，不是重复证明 LightGBM 分类器本身的有效性，而是检查临床主风险、遗传修正因子和行为修正因子能否在同一服务链中被稳定组织为综合风险信号。与第 4 章的方法定义一致，融合服务在 \codeid{fusion_service.py} 中对临床风险结果、遗传修正因子和行为修正因子进行乘性整合，并通过概率裁剪保持输出稳定。

就本轮能够直接复核的证据而言，融合模块的验证主要体现为输出结构和服务行为的一致性，而不是离线消融分数的重新计算。综合分析接口会返回可供前端展示和后续推演复用的风险报告，服务侧也保留了对潜在高风险情形的工程化标签表达。因此，这部分更适合得出的结论是：融合链路已经能够把临床、遗传和行为证据组织为统一的综合风险输出；至于更细粒度的离线消融优劣排序，仍需依赖完整训练日志和专门实验表格支持，不宜在本轮正文中写成定量结论。

\subsection{干预推演案例分析}
干预推演验证对应 \codeid{backend/services/projection_service.py} 的两类场景：一类是自然老化场景，通过增加年龄并对收缩压、空腹血糖和 BMI 施加缓慢上升趋势，观察未来风险变化；另一类是生活方式干预场景，通过设定如 \codeid{weight_loss_percent} 等可控变量，模拟体重下降后对血压、血糖和综合风险的联动影响。服务返回结果同时包含 \codeid{base_risk_max}、\codeid{new_risk_max} 和 \codeid{risk_reduction_percent} 等字段，说明系统不仅能够给出静态风险快照，还能够输出干预前后风险差异。

从代码与结果结构的一致性看，当前干预推演更适合被理解为“规则化情景模拟”而非严格因果模型求解。其优势在于能够直接复用第 4 章中的融合风险链路，为用户提供具有方向性的对比结果；其边界在于结果主要用于辅助解释和方案比选，而不应被表述为临床级疗效预测。对于本科论文而言，这种定位既符合实现真实能力，也能体现平台从风险识别向干预支持延伸的价值。

\section{系统功能测试与结果分析}
\label{sec:functional_test}
\subsection{平台核心功能测试}
系统功能验证采用“仓库级回归 + 浏览器场景验证”的双层结构。后端部分使用 \codeid{pytest} 与 FastAPI TestClient 对主路由、OCR 上传、综合分析、RAG 检索、聊天接口、会话回放和运行时降级路径进行回归验证；浏览器部分使用 Playwright 对 Dr. AI 接管提示、OCR 引导补全和主要页面可加载性进行场景回归。与旧版本测试章节不同，本节不再展开依赖注入、内存数据库和 Mock 细节，而只保留能够直接说明系统可运行性的结果。

在当前本地环境中，仓库级回归命令 \codeid{python -m pytest tests -q} 的执行结果为 \(232/232\) 全部通过；浏览器端运行 \codeid{dr-ai-takeover.spec.js} 与 \codeid{ocr-guided-completion.spec.js} 两组关键场景测试，在 Chromium、Firefox 与 WebKit 三类浏览器内核下共 \(21/21\) 通过。这说明系统不仅在接口层保持了稳定契约，也能在页面交互层稳定完成 OCR 状态展示、引导补全、接管提示渲染和主要页面加载等核心链路。

\subsection{OCR与健康问答功能测试}
需要说明的是，本节测试重点在于验证 OCR 上传、状态回传、结构化结果回填和问答链路的系统行为，并不单独评测第三方 OCR 或大语言模型服务本身的识别率与医学回答能力。

从业务链路看，平台的关键功能验证可以归纳为三类代表性场景。其一，根据现有 QA 记录，真实 PDF 上传在 OCR provider 不可用的环境下能够返回 \codeid{stored_unprocessed} 并触发“已保存待识别”状态展示，这说明文档上传链路在降级条件下仍能完成入库和状态回传。其二，本轮本地 Playwright 回归进一步验证了 \codeid{partial_success}、\codeid{analysis_context} 横幅、缺失字段提示和页面主路由加载等界面行为，说明 OCR 引导补全路径和主要页面状态切换具有可重复的前端回归覆盖。其三，Dr. AI 相关浏览器回归验证了接管提示、历史消息回放和结构化元数据渲染，说明第 5 章所述的受控问答链已经能够在真实页面交互中被稳定消费。

与第 5 章的实现描述相对应，这些功能测试并不追求覆盖所有页面与全部异常组合，而是围绕论文主线选取最能体现主业务链的关键路径进行验证。由此，本节更稳妥的结论是：在当前代码版本中，平台从数据输入、风险分析到受控问答输出的主要交互链可重复执行，且 OCR 降级状态、引导补全语义和问答结构化结果都已有明确的回归测试覆盖。不过，真实 OCR 自动回填仍然受当前 provider 可用性限制，因而不宜把该部分写成已在本轮环境下完整验证的事实。

\section{Agent模块补充验证}
\label{sec:agent_harness_eval}
\subsection{典型场景行为验证}
除系统级功能验证外，本文还对 Agent 运行语义进行了受控补充评测。相关评测由行为评测脚本、场景清单和基线产物共同完成，其中核心脚本为 \codeid{agent_behavior_eval.py}。场景集合固定覆盖急症分流、报告解读、趋势解释、用药问答、证据不足拒答和工具失败降级六类关键语义路径。该设计的重点不在于比较开放世界下的医学正确率，而在于验证固定输入条件下，Agent 是否能够稳定输出预期的车道、裁决、回答模式、证据充分性与接管标记。

\section{本章小结}
本章从训练侧验证、系统功能测试和 Agent 补充评测三个层面给出了系统验证材料。训练脚本与融合服务的核对表明，平台已具备组织临床、遗传和行为证据的综合风险分析基础；系统功能测试表明，画像输入、OCR 状态回传、综合分析与健康问答等核心路径在当前代码版本中能够稳定运行；Agent 补充验证则说明其运行语义具备可回归、可审计和可解释特征。综合来看，当前证据支持“综合风险分析主链可运行、关键交互可回归、问答策略受控”这一结论，同时保留 OCR 实时结构化解析和完整离线 benchmark 仍受环境与日志材料限制的边界。
