\chapter{实验与测试分析}

本章围绕“模型效果、系统功能与 Agent 运行稳定性”三条证据链，对前文提出的方法与实现进行验证。考虑到本科论文正文篇幅限制，本章不再保留过细的压测脚本说明、缓存时序拆解和大段测试框架实现细节，而是仅保留能够直接支撑论文结论的实验结果与分析。整体上，本章重点回答三个问题：多模态风险评估链路是否具备有效性，平台关键业务路径是否可稳定运行，以及 Agent 问答模块是否能够在固定输入条件下保持可回归、可解释的行为边界。

\section{风险预测与融合效果分析}
\subsection{疾病风险预测结果分析}
慢病风险预测模型由 \texttt{ai\_core/train\_risk\_models.py} 训练完成，针对各目标病种独立构建 LightGBM 二分类器。训练阶段采用分层抽样划分训练集与测试集，并通过 \texttt{is\_unbalance=True} 处理阳性样本占比较低的问题。与仅追求分类分数不同，当前实验特别强调防泄漏控制：脚本在每个病种训练前依据 \texttt{LEAKAGE\_MAPPING} 剔除与目标诊断高度重叠的变量，从而避免将诊断同义特征直接作为预测依据。该设置保证了实验结果更接近真实筛查场景，也使在线服务输出与训练阶段的特征边界保持一致。

结合训练脚本与服务侧运行逻辑可以看到，临床风险模型的主要价值不在于追求某一疾病的极端高分，而在于为后续融合模块提供稳定、可解释的初始风险输入。与此相对应，行为风险模型和营养视觉模型在当前系统中主要承担辅助修正与扩展输入作用：前者为行为风险修正因子提供支持，后者为饮食与营养记录补充可结构化信息。因此，本章不再将二者作为与临床主模型并列的独立实验重点，而是将其视作多模态融合链路中的辅助证据来源。

\subsection{多模态融合消融实验}
多模态融合部分围绕“仅临床风险”“临床风险叠加遗传因子”“临床风险叠加遗传与行为因子”三种设置展开比较，其核心目标不是重复证明 LightGBM 分类器本身的有效性，而是考察融合后概率输出是否更适合作为健康管理平台中的综合风险信号。与第 4 章的方法定义一致，融合服务在 \texttt{fusion\_service.py} 中对临床风险结果、遗传修正因子和行为修正因子进行乘性整合，并通过 \texttt{clip([0.1,99.9])} 保持结果稳定。

本研究在实验分析上更关注融合后的概率质量而非单一阈值下的命中率，因此采用 Brier Score 与校准特性作为重点参考指标。现有实验设计表明，引入遗传和行为证据后，系统能够在保持临床主模型可解释性的同时，进一步区分“当前临床表型尚未明显异常但遗传易感性偏高”的潜在风险个体。服务侧的 \texttt{Potential} 标签正是对这一场景的工程化表达。换言之，融合模块的主要收益并不只是抬高某一项分数，而是使风险输出更适合面向主动健康管理的分层筛查与持续跟踪。

\subsection{干预推演案例分析}
干预推演验证对应 \texttt{backend/services/projection\_service.py} 的两类场景：一类是自然老化场景，通过增加年龄并对收缩压、空腹血糖和 BMI 施加缓慢上升趋势，观察未来风险变化；另一类是生活方式干预场景，通过设定如 \texttt{weight\_loss\_percent} 等可控变量，模拟体重下降后对血压、血糖和综合风险的联动影响。服务返回结果同时包含 \texttt{base\_risk\_max}、\texttt{new\_risk\_max} 和 \texttt{risk\_reduction\_percent} 等字段，说明系统不仅能够给出静态风险快照，还能够输出干预前后风险差异。

从代码与结果结构的一致性看，当前干预推演更适合被理解为“规则化情景模拟”而非严格因果模型求解。其优势在于能够直接复用第 4 章中的融合风险链路，为用户提供具有方向性的对比结果；其边界在于结果主要用于辅助解释和方案比选，而不应被表述为临床级疗效预测。对于本科论文而言，这种定位既符合实现真实能力，也能体现平台从风险识别向干预支持延伸的价值。

\section{系统功能测试与结果分析}
\label{sec:functional_test}
\subsection{平台核心功能测试}
系统功能验证采用“仓库级回归 + 浏览器场景验证”的双层结构。后端部分使用 \texttt{pytest} 与 FastAPI TestClient 对主路由、OCR 上传、综合分析、RAG 检索、聊天接口、会话回放和运行时降级路径进行回归验证；浏览器部分使用 Playwright 对 Dr. AI 接管提示、OCR 引导补全和主要页面可加载性进行真实交互验证。与旧版本测试章节不同，本节不再展开依赖注入、内存数据库和 Mock 细节，而仅保留能够直接说明系统可运行性的结果。

在当前本地环境中，仓库级回归命令 \texttt{python -m pytest tests -q} 的执行结果为 \(232/232\) 全部通过；浏览器端在 Chromium 环境下运行 \texttt{dr-ai-takeover.spec.js} 与 \texttt{ocr-guided-completion.spec.js} 两组关键场景测试，共 \(7/7\) 通过。这说明系统不仅在接口层保持了稳定契约，也能在真实页面交互中完成 OCR 状态展示、引导补全、接管提示渲染和主要页面加载等核心链路。

\subsection{OCR与健康问答功能测试}
从业务链路看，平台的关键功能验证可归纳为三类代表性场景。其一，用户通过档案录入和体检报告上传形成画像输入，系统完成 OCR 状态回传、结构化摘要保存以及分析上下文刷新，验证了“文档感知$\rightarrow$风险分析”的前置链路。其二，用户在聊天界面发起健康咨询后，系统能够返回包含回答文本、裁决摘要、证据标签和接管提示的结构化结果，验证了第 5 章 Agent 运行链在真实接口中的可执行性。其三，当用户画像或报告信息发生更新时，前后端状态能够同步刷新并驱动后续分析结果变化，验证了平台并非静态页面集合，而是具备连续交互能力的健康管理原型系统。

与第 5 章的实现描述相对应，这些功能测试并不追求覆盖所有页面与所有异常组合，而是围绕论文主线选取最能体现“平台闭环”的关键路径进行验证。由此，本节的结论可以概括为：系统已具备从数据输入、风险分析到受控问答输出的基本闭环能力，且关键交互在当前代码版本中可重复执行。

\section{Agent模块补充验证}
\label{sec:agent_harness_eval}
\subsection{典型场景行为验证}
除系统级功能验证外，本文还对 Agent 运行语义进行了受控补充评测。相关评测由行为评测脚本、场景清单和基线产物共同完成，其中核心脚本为 \path{agent_behavior_eval.py}。场景集合固定覆盖急症分流、报告解读、趋势解释、用药问答、证据不足拒答和工具失败降级六类关键语义路径。该设计的重点不在于比较开放世界下的医学正确率，而在于验证固定输入条件下，Agent 是否能够稳定输出预期的车道、裁决、回答模式、证据充分性与接管标记。

在当前本地环境中，Harness 运行结果显示 \texttt{scenario\_count=6}、\texttt{passed\_count=6}、\texttt{failed\_count=0}。这说明第 5 章提出的意图分流、工具约束、证据门控与回答策略控制，在受控测试条件下能够维持稳定行为边界。对于毕业论文而言，这类结果的意义在于证明 Agent 模块不是不可回归的黑箱问答，而是可以进行结构化验证的受控运行链。

\subsection{安全性与一致性分析}
进一步地，\texttt{backend/eval/artifacts/agent\_behavior\_results.json} 中记录的 \texttt{baseline\_match=true} 表明当前运行结果与冻结基线快照保持一致。结合测试文件 \texttt{tests/test\_agent\_behavior\_eval\_harness.py} 可以看出，该评测框架能够区分“运行时行为失败”和“基线陈旧失配”两类情形，从而更适合承担回归一致性验证任务，而非临床正确性验证任务。

\section{本章小结}
本章从模型效果、系统功能和 Agent 补充验证三个层面给出了论文系统的实验依据。风险模型与融合分析表明，平台已具备将临床、遗传和行为证据组织为综合风险信号的能力；系统功能测试表明，画像输入、OCR 解析、综合分析与健康问答等核心路径在当前代码版本中能够稳定运行；Agent 补充验证则进一步说明其运行语义具备可回归、可审计和可解释特征。综合而言，本论文系统已经形成“模型可用、平台可运行、问答可受控”的实验支撑，为后续总结与展望提供了较为稳固的依据。
