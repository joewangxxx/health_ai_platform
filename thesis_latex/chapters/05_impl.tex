\chapter{系统实现}

在完成总体设计与关键算法分析后，本章进一步说明平台如何在现有代码框架中落地实现。与第 4 章偏重算法主线不同，本章关注的是服务组织方式、前后端协同、Agent 运行链以及部署运行路径。为避免实现章再次滑向“工程说明书”，本章只保留与论文主线直接相关的实现内容，即风险评估、OCR 报告解析、健康问答 Agent、核心前端交互与容器化集成；而过细的缓存键设计、载荷模式字段和后台数据中枢细节不再在正文中展开。

\section{后端核心服务实现}

平台后端采用 FastAPI 作为主要服务入口，应用实例在 \texttt{backend/main.py} 中创建，并通过 \texttt{lifespan} 生命周期钩子完成可选模型、风险引擎、基因引擎与融合引擎的延迟加载。这样做的直接目的是将“应用导入”和“模型初始化”两个阶段分离，从而降低启动时的强耦合度，并为后续的 OCR、风险分析、问答等路由提供统一的运行时依赖。需要强调的是，当前系统仍属于单后端进程承载多类业务服务的实现方式，而非严格意义上的多后端微服务拆分架构，因此本节的描述以模块化服务组织为主，不夸大其分布式程度。

\subsection{风险评估服务实现}

风险评估服务的实现主链由入口文件 \texttt{main.py}、风险服务文件 \texttt{risk\_engine.py}、融合服务文件 \texttt{fusion\_service.py} 和分析接口共同构成。系统在启动阶段分别加载临床、基因和融合三类风险引擎，并在综合分析接口中组织临床数据、用户 SNP 数据和默认设备状态，形成与第 4 章算法一致的推理输入。这里的实现重点不是再次推导模型公式，而是保证训练阶段保存的模型包、特征映射和运行时输入能够稳定对齐。

从接口行为看，前端或业务侧在调用综合分析接口后，会得到结构化风险报告，其中包含病种级概率、风险分级与部分解释信息。若融合引擎不可用，主程序中还提供了降级分支，用于返回基于临床数据的简化风险结果。这一设计说明平台在实现层采用了“优先保证分析可返回，再区分是否进入完整融合路径”的策略，其目标是提升服务可用性，而不是保证所有请求都严格走同一条满配推理链。

\subsection{OCR解析服务实现}

体检报告解析由 OCR 服务文件 \texttt{ocr\_service.py} 与接口文件 \texttt{ocr.py} 协同完成。当前实现中，\texttt{MedicalOCRService} 负责 PDF 转图片、OCR 文本抽取、正则初筛以及大模型结构化解析，接口层则负责接收上传文件、创建 \texttt{MedicalDocument} 记录、保存规范化后的结构化摘要与处理状态，并在成功后触发缓存失效。这样的职责划分使“文档解析逻辑”和“文档持久化逻辑”保持分离，便于后续对 OCR 供应商或解析策略进行替换。

需要特别说明的是，OCR 链路在当前系统中并非“只要上传就一定得到完整结构化结果”。从代码实现看，系统显式保留了 \texttt{stored\_unprocessed}、\texttt{partial\_success} 和降级返回路径，这意味着正文中应当将其描述为“带有状态回传与失败兜底的智能解析服务”，而不是无条件成功的自动识别模块。这种写法既符合实际实现边界，也更适合在答辩中回应“识别失败时系统如何处理”的问题。

\subsection{数据管理与任务调度实现}

除面向普通用户的分析与问答接口外，平台还保留了若干管理员侧的数据上传与训练入口。相关逻辑主要位于后端入口和管理服务模块中，并借助 FastAPI 的 \texttt{BackgroundTasks} 执行临床数据处理、GWAS 清洗和模型训练等后台任务。这里的实现特点是轻量级、进程内和任务目标明确：它能够满足论文原型系统对“上传后异步处理”的需要，但并未引入消息队列、分布式调度器或独立任务中间件。因此，在学术表达上更合适的说法是“后台任务调度支持”，而不是“统一任务编排平台”。

\section{前端核心功能实现}
\label{sec:frontend_impl}

前端采用 Vue 3 与 Pinia 组织用户交互逻辑，核心路由由 \texttt{router/index.js} 管理，主要状态仓库则由 \texttt{healthStore.js} 与 \texttt{authStore.js} 承担。实现上，系统并未追求复杂的前端框架创新，而是围绕“健康档案录入、风险结果展示、对话与推演交互”三个主任务组织页面。因此，本节的重点不在于枚举所有页面组件，而在于说明关键用户流程如何与后端分析链衔接。

\subsection{用户健康档案与报告上传功能}

在临床信息录入侧，\texttt{ClinicalView.vue} 与状态仓库共同承担了用户画像编辑、OCR 报告上传和结果回填等任务。用户上传体检报告后，前端通过 OCR 上传接口提交表单数据，并将返回的结构化摘要、处理状态和分析上下文写回本地状态；若返回结果中包含可用的结构化数据，则界面进一步将其映射回档案字段，并尝试刷新后端分析上下文与风险报告。这样的流程设计使 OCR 不只是孤立的上传能力，而是直接嵌入到“档案补全 $\rightarrow$ 风险分析”的前端主路径中。

\subsection{风险展示与可视化功能}

风险展示功能主要由 \texttt{DashboardView.vue} 与 \texttt{healthStore.js} 实现。前端在组织完临床字段与基因数据后，会调用 \texttt{/analyze/comprehensive} 获取结构化风险结果，并将其写入统一的 \texttt{riskReport} 状态，再由仪表盘图表和疾病名称映射模块完成可视化渲染。这里的实现重点是“结果状态统一归口”：分析接口、临床页、生活方式页和时间线页都围绕同一份风险快照展开更新，避免不同页面各自维护一份互不一致的分析结果。

\subsection{干预建议与交互流程实现}

除静态风险展示外，前端还通过时间线视图和问答视图承接更具交互性的分析过程。前者通过 \texttt{/analysis/simulate/future} 和 \texttt{/analysis/simulate/intervention} 接口展示自然老化与干预场景下的结果差异，后者则在 \texttt{DrAI.vue} 中通过 \texttt{/chat/send} 与 \texttt{/chat/stream} 接口提供增量式对话体验，并展示证据标签、治理摘要、接管提示与证据面板。由此可见，前端在当前论文系统中的角色并非单纯的数据展示终端，而是将分析、解释和问答三类能力组织为连续交互流程的界面层实现。

\section{Agent架构设计与实现}
\label{sec:agent_impl}

Agent 模块是本论文在系统实现层最具有特色的部分。与常见“直接将用户问题交给大模型生成回答”的问答方式不同，当前实现采用了显式的运行时治理链：先进行意图分流，再组织受限工具调用，随后执行证据门控与回答策略控制，最后将结果写入审计与回放链路。其主要实现由 \texttt{chat\_service.py}、\texttt{agent\_safety.py}、\texttt{agent\_tools.py} 以及与上下文和审计相关的辅助文件共同支撑。因此，本节不是对“Agent 理论”的再次抽象，而是对当前代码中真实存在的治理主链进行归纳。

\subsection{Agent整体执行流程}

\texttt{ChatService} 的 \texttt{chat()} 和 \texttt{stream\_chat()} 最终都汇聚到 \texttt{\_chat\_events()} 这一主执行链中。该链路首先建立或恢复会话，随后执行安全分类，读取用户画像摘要，检索 RAG 上下文，构造规划上下文，选择允许调用的只读工具，再根据工具输出与检索质量进行后置证据评估，最后组织回答文本、治理摘要、证据面板和接管提示等结构化输出。换言之，\texttt{\_chat\_events()} 承担了 Agent 运行时“总装配器”的角色，它把原本分散在不同文件中的分流、检索、工具、预算、门控和回放逻辑串接成一条可追踪的对话执行路径。

从接口形态看，聊天接口文件 \texttt{chat.py} 同时提供普通请求和流式请求两种访问方式，并将消息结构、证据面板、响应裁决和接管提示定义为显式的数据模型。这意味着当前 Agent 的输出不是单一的纯文本回复，而是“回答文本 + 治理元数据”的复合结果。该设计与前端的逐步展示逻辑相匹配，也让审计与测试环节更容易验证每一步运行状态。

\subsection{意图分流与工具调用约束}
\label{sec:lane_engine_impl}

在进入模型生成前，系统先由 \texttt{agent\_safety.py} 中的 \texttt{classify\_query\_safety()} 执行安全分类，输出当前查询所属的车道、路由方式与风险等级。当前实现采用规则驱动而非独立分类模型：它通过模式表和优先级顺序，将查询归入健康咨询、报告解读、趋势回顾、用药相关、诊断敏感和急症分流等车道，并在急症场景下直接短路到安全引导回复。这样的实现方式虽然不属于高复杂度语义分类器，但具有边界清晰、易审计和便于人工规则修正的优势。

在完成车道划分后，系统并不会把全部工具都交给大模型自由探索，而是由 \texttt{ChatService.\_plan\_tools()} 与工具注册表共同决定可调用的受限工具集合。具体来说，规划函数会根据车道默认种子和查询关键词生成候选工具列表，再与按车道返回的白名单求交，并将数量截断在较小上限内。由此，工具调用约束在当前实现中体现为“服务侧先做车道相关筛选，再允许模型在受控集合内调用”，而不是开放式工具自治规划。

\subsection{证据门控与回答策略控制}
\label{sec:evidence_policy_impl}

完成工具调用后，系统进一步通过后置充分性评估函数和会话策略评估函数对现有上下文执行检查。前者综合工具输出、用户画像、报告摘要、趋势信息和 \texttt{rag\_quality\_summary}，判定当前证据属于 \texttt{sufficient}、\texttt{limited} 还是 \texttt{insufficient}；后者再结合车道与策略压力，确定回答模式、免责声明风格以及是否需要接管提示。配套的上下文构建模块则负责在规划阶段和最终回答阶段分别裁剪历史消息、画像摘要、检索文本和工具证据，使有限上下文预算优先服务于当前问题。

从实现边界看，当前系统中的“证据门控”并不是基于医学知识图谱或复杂因果推理的真实性判断，而是围绕结构化工具结果、检索质量和风险车道开展的规则化后置控制。因此，本节在论文中更适合表述为“面向医疗健康问答的运行时受控生成机制”。这种表达既能体现 Agent 模块的亮点，也不会超出代码真实能力。

\subsection{审计与回放机制}
\label{sec:audit_replay_impl}

为提升对话链路的可追溯性，系统在回答生成后将关键信息写入审计记录与答案回放快照。审计侧由 \texttt{agent\_audit.py} 负责构造和持久化运行记录，内容包括车道、规则版本、工具计划来源、上下文预算摘要、风险等级和模型名等；回放侧由 \texttt{agent\_answer\_replay.py} 负责保存面向前端和后续检索的回答快照，其中包含回答文本、证据充分性公开摘要、工具结果摘要和来源引用等信息。两者共同构成了当前 Agent 运行链的“责任留痕层”。

值得注意的是，平台中还存在 \texttt{payload\_normalization.py} 等用于 OCR 摘要、风险快照和药物事实规范化的支撑代码，但它们在本章中不再作为独立主节展开，而被视作审计、工具读取和上下文构建的共享数据底座。这种处理有助于压缩篇幅，也更符合正文主线应围绕“实现了什么关键能力”而不是“支撑模块如何逐一设计”的写作原则。

\section{系统部署与运行流程}
\label{sec:deploy_security_impl}

平台的部署实现以 \texttt{docker-compose.yml} 为中心，将系统组织为前端、后端和 Redis 三个核心容器。其中，后端容器运行 FastAPI 应用并挂载数据库、上传目录和 RAG 知识库目录；前端容器使用 Nginx 承载构建后的 Vue 单页应用；Redis 容器用于缓存高频对话结果和部分运行态状态。这一部署方式说明当前系统在工程上已经具备“单机容器化集成运行”的能力，但尚不应被描述为大规模生产级微服务集群。

\subsection{系统集成方案}

在集成关系上，前端所有页面统一通过 Nginx 反向代理访问后端接口，核心代理规则配置在 \texttt{frontend/nginx.conf} 中：\texttt{/api/} 路径转发到 FastAPI，认证、用户、分析、聊天等直连路径也被统一代理到后端服务，而静态上传文件则经由 \texttt{/static/} 暴露。这样的配置确保了 Vue 路由刷新、前后端通信以及上传文件访问能够在同一入口下协同工作，是当前原型系统可直接部署运行的关键基础。

\subsection{容器化部署与运行流程}

从运行流程看，系统启动时首先由后端 \texttt{lifespan} 钩子完成模型和服务初始化，随后开放风险分析、OCR 和聊天等核心接口；前端在用户登录后通过统一状态仓库获取画像、风险结果与问答上下文；Redis 则承担部分对话缓存和结果复用任务。与原稿中较大篇幅的“全生命周期安全机制”和“治理中枢”描述相比，当前版本更适合概括为：平台已实现面向论文原型系统的容器化部署、接口代理和基础状态持久化，但安全、监控、热更新与运维能力仍属于受限实现，不宜在正文中写成完整的平台级中台体系。

\section{本章小结}

本章从代码实现角度说明了平台各核心模块的落地方式。后端部分以 FastAPI 为统一入口，将风险评估、OCR 报告解析与后台任务调度组织为可调用的服务链；前端部分围绕健康档案、风险展示、干预交互和问答流程实现用户侧体验；Agent 部分则通过分流、受限工具调用、证据门控以及审计回放构成受控问答运行链；部署部分以 Docker Compose、Nginx 和 Redis 完成单机容器化集成。

结合第 4 章的方法设计可以看到，平台在实现层已经形成“算法模型 $\rightarrow$ 服务封装 $\rightarrow$ 前端交互 $\rightarrow$ 运行治理”的闭环结构。下一章将在此基础上进一步验证风险评估、系统功能与 Agent 运行行为的实际效果。
