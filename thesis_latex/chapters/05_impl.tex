\chapter{系统实现}

在完成总体设计与关键算法分析后，本章转而说明主要功能如何在现有代码中落地。与第 4 章偏重方法表达不同，本章更关注服务之间如何协同、前后端如何衔接，以及问答运行链和部署入口如何组织。对本文主线而言，综合风险分析仍是实现层的中心，OCR 更偏向文档输入补全，Agent 更偏向分析结果的解释与反馈。正文只保留与这一主线直接相关的实现内容，而不过度展开缓存键、原始载荷字段和后台管理细节。

\section{后端核心服务实现}

平台后端采用 FastAPI 作为主要服务入口，应用实例在 \codeid{backend/main.py} 中创建，并通过 \codeid{lifespan} 生命周期钩子完成可选模型、风险引擎、基因引擎和融合引擎的延迟加载。这样做的目的，是将应用导入与模型初始化两个阶段分开，降低启动时的强耦合，并为 OCR、风险分析和问答等路由提供统一的运行时依赖。需要说明的是，当前系统仍然是单后端进程承载多类服务的实现方式，而不是严格拆分的多后端微服务架构，因此本节以模块化服务组织为主，不夸大其分布式程度。

\subsection{风险评估服务实现}

风险评估服务的实现主链由入口文件 \codeid{main.py}、风险服务文件 \codeid{risk_engine.py}、融合服务文件 \codeid{fusion_service.py} 以及综合分析接口共同构成。系统在启动阶段分别加载临床、基因和融合三类风险引擎，并在 \codeid{/analyze/comprehensive} 中组织临床数据、用户 SNP 数据和默认设备状态，形成与第 4 章方法一致的推理输入。这里的实现重点不是重新推导模型公式，而是保证训练阶段保存的模型包、特征映射和运行时输入保持稳定对齐。

从接口行为看，前端在调用综合分析接口后，不仅会得到结构化风险报告，还会得到 \codeid{analysis_context}，后者用于提示缺失字段、OCR 导入状态和本轮分析所依赖的上下文信息。若融合引擎不可用，主程序中还保留了降级分支，用于返回基于临床数据的简化风险结果。也就是说，当前实现更强调“先保证分析链可返回，再区分是否进入完整融合路径”，其目标是提高服务可用性，而不是让所有请求都严格经过同一条满配推理链。

\subsection{OCR解析服务实现}

体检报告解析由 OCR 服务文件 \codeid{ocr_service.py} 与接口文件 \codeid{ocr.py} 协同完成。当前实现中，接口层会先接收上传文件并创建 \codeid{MedicalDocument} 记录，再调用 \codeid{MedicalOCRService} 执行文档解析，最后回写规范化后的 \codeid{ocr_summary} 与 \codeid{ocr_processing_status}，并在成功后触发相关缓存失效。这样的组织方式把文档入库和文档解析区分开来，即使 OCR provider 暂时不可用，文档本身仍然可以被保存和追踪。也就是说，OCR 在当前系统中的主要角色是为综合风险分析补全文档输入，而不是独立承担平台的核心分析任务。

在具体识别能力上，系统通过百度智能云 OCR API 完成图片和 PDF 页面中的文字识别。代码层面，\codeid{MedicalOCRService} 先根据文件类型将 PDF 页面转换为图片，再调用百度 OCR 客户端抽取原始文本；平台侧负责结果汇总、字段映射、处理状态封装和与用户档案的衔接。因此，本文不把 OCR 文字识别模型本身作为自研算法贡献，而是将其视为文档输入补全链路中的外部识别能力。

对于 OCR 得到的原始文本，系统进一步通过 OpenAI 兼容接口调用 Moonshot/Kimi 大语言模型服务进行语义结构化，尝试抽取年龄、血压、血糖、血脂、肝肾功能等健康指标，并写入统一的摘要载荷。若模型接口不可用、结构化解析失败或识别文本不足，服务会退回正则抽取或状态回传路径。从代码实现看，系统显式保留了 \codeid{stored_unprocessed}、\codeid{partial_success} 和降级返回路径，前端也会据此区分“已保存待识别”“部分识别”和“识别完成”等状态。因此，正文更适合将其描述为“带有状态回传与失败兜底的文档解析服务”，而不是无条件成功的自动识别模块。

\subsection{数据管理与后台任务支持}

除面向普通用户的分析与问答接口外，后端还保留了少量管理员侧的数据导入、临床训练触发和知识库重建入口。相关逻辑主要位于 \codeid{main.py} 和管理路由模块中，并借助 FastAPI 的 \codeid{BackgroundTasks} 处理部分后台工作。就当前代码而言，这些异步任务更接近原型系统中的轻量支持能力，用于降低上传后处理对在线链路的直接阻塞，而不是独立的任务编排子系统。

因此，本节不把这部分实现写成“统一任务调度平台”。更准确的说法是，系统在主业务链之外提供了有限的后台任务支持，用于服务数据处理、训练触发和知识库维护等辅助流程。这样的表述更符合当前实现边界，也能避免后台能力在正文中压过用户主链。

\section{前端核心功能实现}
\label{sec:frontend_impl}

前端采用 Vue 3 与 Pinia 组织用户交互逻辑，核心路由由 \codeid{router/index.js} 管理，主要状态仓库则由 \codeid{healthStore.js} 与 \codeid{authStore.js} 承担。实现上，系统并未追求复杂的前端层级设计，而是围绕健康档案录入、风险结果展示、问答交互和时间线推演几条主路径组织页面。因此，本节的重点不在于枚举全部组件，而在于说明关键用户流程如何与后端分析链衔接。

\subsection{用户健康档案与报告上传功能}

在临床信息录入侧，\codeid{ClinicalView.vue} 与状态仓库共同承担了用户画像编辑、OCR 报告上传和结果回填等任务。用户上传体检报告后，前端通过 OCR 上传接口提交表单数据，并将返回的结构化摘要、处理状态和分析上下文写回本地状态；若返回结果中包含可用的结构化数据，界面会进一步将其映射回档案字段，并尝试刷新后端分析上下文与风险报告。这样的流程设计使 OCR 不再是孤立的上传能力，而是直接嵌入到“档案补全 $\rightarrow$ 风险分析”的前端主路径中。

\codeid{ClinicalView.vue} 还会根据 \codeid{ocr_processing_status} 展示“已保存待识别”“部分识别”等状态提示，并根据 \codeid{analysis_context} 提示当前缺失字段和分析上下文。这意味着 OCR 上传后的反馈并非只有一次性弹窗，而是会继续保留在页面状态中，供用户决定是直接保存、补录指标，还是重新发起分析。

\subsection{风险展示与可视化功能}

风险展示功能主要由 \codeid{DashboardView.vue} 与 \codeid{healthStore.js} 实现。前端在组织完临床字段与基因数据后，会调用 \codeid{/analyze/comprehensive} 获取结构化风险结果，并将其写入统一的 \codeid{riskReport} 状态，再由仪表盘图表和疾病名称映射模块完成可视化渲染。与风险结果一起维护的还有 \codeid{analysisContext}，两者共同构成前端后续页面判断“当前快照是否可直接复用、是否需要重新分析”的基础。

这里的实现重点是结果状态的统一归口。临床页、仪表盘页以及时间线相关页面都围绕同一份风险快照展开更新，避免不同页面各自维护一份互不一致的分析结果。这种设计虽然增加了状态仓库的责任，但能让风险展示、指标补录和后续问答共享同一套分析上下文。

\subsection{干预建议与交互流程实现}

除静态风险展示外，前端还通过时间线视图和问答视图承接更具交互性的分析过程。前者通过 \codeid{/analysis/simulate/future} 和 \codeid{/analysis/simulate/intervention} 接口展示自然老化与干预场景下的结果差异，当前实现中的干预参数主要围绕 \codeid{weight_loss_percent} 等目标展开；后者则在 \codeid{DrAI.vue} 中通过 \codeid{/chat/send} 与 \codeid{/chat/stream} 接口提供增量式对话体验，并展示证据标签、治理摘要、接管提示、建议卡和证据面板。

需要指出的是，\codeid{DrAI.vue} 不仅负责渲染回答文本，还承担了历史会话切换、重命名、置顶、归档恢复和流式状态展示等交互逻辑；当流式链路不可用时，界面会退回普通请求模式。由此可见，前端在当前系统中的角色并非单纯的数据展示终端，而是把分析、解释和问答组织为可连续操作的交互界面。

\section{Agent架构设计与实现}
\label{sec:agent_impl}

Agent 模块是本论文在系统实现层的重要交互部分。与常见“直接将用户问题交给大模型生成回答”的问答方式不同，当前实现采用了显式的运行时治理链：先进行意图分流，再组织受限工具调用，随后执行证据门控与回答策略控制，最后将结果写入审计与回放链路。其主要实现由 \codeid{chat_service.py}、\codeid{agent_safety.py}、\codeid{agent_tools.py} 以及与上下文和审计相关的辅助文件共同支撑。因此，本节不是把 Agent 写成独立分析中枢，而是说明它如何在综合风险分析结果之上承担解释、问答和反馈职责。

在模型服务接入方面，当前后端通过配置项 \codeid{OPENAI_BASE_URL} 与 \codeid{OPENAI_MODEL} 接入 Moonshot/Kimi 的 OpenAI 兼容接口，并由 \codeid{ChatService} 在工具规划和最终回答阶段按需调用模型生成能力。需要说明的是，平台并不直接依赖模型的自由生成结果来完成医疗健康问答，而是在模型调用前后加入用户画像读取、RAG 上下文组织、只读工具白名单、上下文预算、证据充分性评估和审计回放等约束机制。由此，Kimi API 在系统中承担外部语言生成与语义理解服务的角色，论文的实现重点则落在受控编排和可追踪运行链路上。

\subsection{Agent整体执行流程}

\codeid{ChatService} 的 \codeid{chat()} 和 \codeid{stream_chat()} 最终都汇聚到 \codeid{_chat_events()} 这一主执行链中。该链路首先建立或恢复会话，随后执行安全分类，读取用户画像摘要，检索 RAG 上下文\cite{zhang2025medicalrag}，构造规划上下文，选择允许调用的只读工具，再根据工具输出与检索质量进行后置证据评估，最后组织回答文本、治理摘要、证据面板和接管提示等结构化输出。换言之，\codeid{_chat_events()} 承担了 Agent 运行时的总装配角色，把原本分散在不同文件中的分流、检索、工具、预算、门控和回放逻辑串接成一条可追踪的对话执行路径。

从接口形态看，聊天路由不仅提供 \codeid{/chat/send} 和 \codeid{/chat/stream}，还提供历史会话列表、消息回放、重命名、归档恢复和置顶等接口。这意味着当前 Agent 的输出和状态管理都不是单一的纯文本回复，而是“回答文本 + 会话元数据 + 运行元数据”的复合结果。这样的接口组织与前端的历史会话侧边栏和增量展示逻辑相匹配，也让审计与测试环节更容易验证每一步运行状态。

\subsection{意图分流与工具调用约束}
\label{sec:lane_engine_impl}

在进入模型生成前，系统先由 \codeid{agent_safety.py} 中的 \codeid{classify_query_safety()} 执行安全分类，输出当前查询所属的车道、路由方式与风险等级。当前实现采用规则驱动而非独立分类模型：它通过模式表和优先级顺序，将查询归入健康咨询、报告解读、趋势回顾、用药相关、诊断敏感和急症分流等车道，并在急症场景下直接短路到安全引导回复。这样的实现方式虽然不属于高复杂度语义分类器，但具有边界清晰、易审计和便于人工规则修正的优势。

在完成车道划分后，系统并不会把全部工具都交给大模型自由探索，而是由 \texttt{ChatService.\_plan\_tools()} 与工具注册表共同决定可调用的受限工具集合。具体来说，规划函数会根据车道默认种子和查询关键词生成候选工具列表，再与按车道返回的白名单求交，并将数量截断在较小上限内。由此，工具调用约束在当前实现中体现为“服务侧先做车道相关筛选，再允许模型在受控集合内调用”，而不是开放式工具自治规划。

\subsection{证据门控与回答策略控制}
\label{sec:evidence_policy_impl}

完成工具调用后，系统进一步通过后置充分性评估函数和会话策略评估函数对现有上下文执行检查。前者综合工具输出、用户画像、报告摘要、趋势信息和 \codeid{rag_quality_summary}，判定当前证据属于 \codeid{sufficient}、\codeid{limited} 还是 \codeid{insufficient}；后者再结合车道与策略压力，确定回答模式、免责声明风格以及是否需要接管提示。配套的上下文构建模块则负责在规划阶段和最终回答阶段分别裁剪历史消息、画像摘要、检索文本和工具证据，使有限上下文预算优先服务于当前问题。

从实现边界看，当前系统中的“证据门控”并不是基于医学知识图谱或复杂因果推理的真实性判断，而是围绕结构化工具结果、检索质量和风险车道开展的规则化后置控制。因此，本节在论文中更适合表述为“面向医疗健康问答的运行时受控生成机制”。这种表达既能体现 Agent 模块的特点，也不会超出代码真实能力。

\subsection{审计与回放机制}
\label{sec:audit_replay_impl}

为提升对话链路的可追溯性，系统在回答生成后将关键信息写入审计记录与答案回放快照。审计侧由 \codeid{agent_audit.py} 负责构造和持久化运行记录，内容包括车道、规则版本、工具计划来源、上下文预算摘要、风险等级和模型名等；回放侧由 \codeid{agent_answer_replay.py} 负责保存面向前端和后续检索的回答快照，其中包含回答文本、证据充分性摘要、工具结果摘要和来源引用等信息。历史会话再次打开时，前端据此恢复已保存的回答内容以及相关结构化元数据，而不是重新拼接一次旧响应。

值得注意的是，平台中还存在 \codeid{payload_normalization.py} 等用于 OCR 摘要、风险快照和药物事实规范化的支撑代码，但它们在本章中不再作为独立主节展开，而是被视作审计、工具读取和上下文构建所共享的数据底座。这样的处理有助于压缩篇幅，也更符合正文主线应围绕“实现了什么关键能力”而不是“支撑模块如何逐一设计”的写作原则。

\section{系统部署与运行流程}
\label{sec:deploy_security_impl}

平台的部署实现以 \codeid{docker-compose.yml} 为中心，将系统组织为前端、后端和 Redis 三个容器。其中，后端容器运行 FastAPI 应用并挂载数据库、上传目录和 RAG 知识库目录；前端容器使用 Nginx 承载构建后的 Vue 单页应用；Redis 在当前 Compose 方案中承担缓存和部分结果复用角色。这一部署方式说明系统已经具备单机容器化集成运行能力，但尚不应被描述为大规模生产级微服务集群。

\subsection{系统集成方案}

在集成关系上，前端所有页面统一通过 Nginx 反向代理访问后端接口，核心代理规则配置在 \codeid{frontend/nginx.conf} 中：\codeid{/api/} 路径转发到 FastAPI，认证、用户、分析、聊天等直连路径也被统一代理到后端服务，而静态上传文件则经由 \codeid{/static/} 暴露。这样的配置既处理了 Vue 单页路由刷新问题，也保证了前后端通信和上传文件访问能够在同一入口下协同工作，是当前原型系统可以直接部署运行的关键基础。

\subsection{容器化部署与运行流程}

从运行流程看，系统启动时首先由后端 \codeid{lifespan} 钩子完成风险引擎、OCR 相关服务和聊天运行时依赖的初始化，随后开放综合分析、OCR 和聊天等核心接口；前端在用户登录后通过统一状态仓库获取画像、风险结果与问答上下文；Redis 则承担部分缓存和结果复用任务。与原稿中较大篇幅的“全生命周期安全机制”和“治理中枢”描述相比，当前版本更适合概括为：平台已实现面向论文原型系统的容器化部署、接口代理和基础状态保持，但安全、监控、热更新与运维能力仍属于受限实现，不宜在正文中写成完整的平台级中台体系。

\section{本章小结}

本章从代码实现角度说明了平台各核心模块的落地方式。后端部分以 FastAPI 为统一入口，将综合风险分析服务组织为主链，并通过 OCR 报告处理完成文档输入补全，通过有限的后台任务支持主业务链运行；前端部分围绕健康档案、风险展示、情景推演和问答流程形成连续交互；Agent 部分则在分析结果之上通过分流、受限工具调用、证据门控以及审计回放构成受控问答运行链；部署部分以 Docker Compose、Nginx 和 Redis 完成单机容器化集成。

结合第 4 章的方法设计可以看到，平台在实现层已经形成从算法方法到服务封装、再到前端交互和运行治理的实现链路。下一章将在此基础上进一步验证风险评估、系统功能与 Agent 运行行为的实际效果。
