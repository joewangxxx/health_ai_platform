\chapter{相关理论与关键技术}
\label{sec:theory}

本章只讨论后续章节确实会用到的理论与技术背景，重点包括多模态健康数据融合、疾病风险预测与情景推演，以及 OCR、RAG 与 Agent 问答等关键技术。与第 4 章的算法设计和第 5 章的系统实现不同，本章不展开具体部署、接口组织或测试过程，而是先把后文会反复出现的概念和技术关系说明清楚。

\section{多模态健康数据融合基础}
\subsection{健康数据的多源异构性}
健康管理所使用的数据并非来自单一来源。结构化临床指标反映个体在某一时间点的体征和检验状态，基因数据描述相对稳定的遗传易感性，行为或设备观测则更多体现短时变化的生活方式和生理波动。这几类数据在时间尺度、观测粒度和噪声特征上都不相同，因此单一数据源往往只能呈现个体风险的一部分。医疗人工智能应用中的数据集标准化研究也表明，字段定义、采集语境和质量约束会直接影响后续模型与系统解释的可靠性\cite{arora2023healthdatasetstandards}。本文平台正是在这一背景下，将结构化画像、体检报告解析结果、基因信息和行为相关状态组织为互补证据，用于形成更适合主动健康管理的综合风险表示。

\subsection{风险融合的基本思想}
在当前实现中，临床风险评估结果作为基础先验，遗传与行为相关信息作为修正因子参与综合风险计算。其核心思想可以概括为
\begin{equation}
    P_{\mathrm{fusion}}=\operatorname{clip}(P_c\cdot \alpha \cdot \beta,\;0.1,\;99.9),
    \label{eq:fusion_theory_compact}
\end{equation}
其中 \(P_c\) 表示基于结构化健康指标得到的临床风险先验，\(\alpha\) 表示遗传风险修正因子，\(\beta\) 表示行为风险修正因子。需要说明的是，上式更适合作为受贝叶斯思想启发的工程化融合表达，而不是严格意义上的概率图模型后验推断。与之对应的代码实现位于 \codeid{backend/services/fusion_service.py} 的 \codeid{calculate_composite_risk()} 中，其作用是把不同来源的证据整理为统一的综合风险输出。

除静态融合外，现有代码中还保留了将实时心率等短时信号作为事件触发信息、对当前风险快照做有限更新的逻辑。这种机制的作用是让融合结果能够对短时异常状态作出反馈，但其本质仍然是基于规则的工程更新，而不是连续时间医学状态空间估计。

\section{疾病风险预测与情景推演基础}
\subsection{结构化健康风险预测}
疾病风险预测是本文平台的基础分析能力。对于结构化健康数据，梯度提升树模型在处理非线性关系、缺失值和异质特征方面具有较好的工程适应性，因此本文采用 LightGBM 作为临床风险预测的主要建模工具。训练脚本 \codeid{ai_core/train_risk_models.py} 针对不同目标病种分别构建二分类模型，并通过分层抽样与泄漏特征剔除机制，尽量避免将与诊断定义高度重叠的变量直接带入模型。

在此基础上，遗传风险评分用于补充长期易感性信息，行为相关服务则用于提供辅助修正证据。它们在系统中的角色并不是独立给出最终判断，而是帮助平台在临床主风险之外吸收更多维度的信息。因此，从论文主线看，本节更关注“如何形成稳定的临床主风险输入”，而不是对每一个辅助模块都分别展开完整算法论证。

\subsection{面向干预的情景推演}
健康管理平台不仅需要识别当前风险，还需要支持对未来风险变化的辅助分析。基于这一需求，本文在风险评估基础上引入情景推演思路：一方面模拟年龄增长、体重变化、血压和血糖波动对未来风险的影响，另一方面比较干预条件调整后风险可能出现的变化方向。其核心目标不是给出严格的临床因果结论，而是提供可比较的风险差异，用于辅助用户理解不同方案可能带来的结果变化。

对应到实现层，\codeid{backend/services/projection_service.py} 通过复用融合风险引擎，对“当前状态”和“调整后状态”分别计算风险结果，并输出风险变化幅度。由此可见，本文所说的“干预推演”更适合理解为基于规则扰动和同一风险引擎复算的情景分析机制，而不是完整的结构因果模型求解。

\section{OCR、RAG与Agent关键技术}
\subsection{OCR与知识增强问答}
在真实健康管理场景中，用户提供的信息并不总是完全结构化。体检报告、检验单和其他医疗文档通常以 PDF 或图像形式存在，因此需要先通过 OCR 将关键信息提取为可计算字段，再与用户画像共同进入后续分析链路。本文平台中的 OCR 服务由 \codeid{backend/services/ocr_service.py} 实现，其核心作用是把半结构化医学文档转化为后续可利用的结构化摘要，而不是替代人工完成完整临床解释。就当前实现而言，OCR 处理结果还区分为成功、部分成功和待后续处理等状态，这也说明文档解析在平台中被视为分析输入的一部分，而不是天然稳定可靠的单步结果。

对于医学知识问答，平台采用检索增强生成思路。其基本过程是先从知识库中检索与当前问题相关的文本证据，再将检索结果与用户画像、报告摘要等信息共同送入回答生成链路。近年的医学问答研究也表明，检索增强和长上下文组织能够提升模型对外部证据的利用能力\cite{zhang2025medicalrag}。对应实现位于 \codeid{backend/services/rag_service.py}，其 \codeid{search_context_with_quality()} 不仅返回检索文本，也返回检索状态和质量摘要。这说明平台中的 RAG 不只是简单的“向量检索 + 文本拼接”，而是带有检索可用性和证据质量判断的知识增强支撑机制。

\subsection{面向医疗场景的Agent基本机制}
与通用开放式问答不同，医疗健康场景对回答边界、风险提示和工具使用约束更加敏感。基于这一特点，本文平台中的 Agent 不采用完全开放的自由生成方式，而是在回答前增加安全分流、工具约束和证据充分性判断等步骤。相关能力主要由 \codeid{backend/services/agent_safety.py}、\codeid{backend/services/chat_service.py} 和 \codeid{backend/services/agent_tools.py} 协同实现。其基本流程包括先判断问题所属风险车道，再限定可用工具集合，随后结合用户画像、检索证据和工具输出判断当前证据是否足以支持回答，最后生成受约束的回复结果。

需要强调的是，本章只讨论 Agent 的基本技术思想及其在医疗场景中的适配方式，不在此处展开完整的运行链和治理细节。相关实现将在第 5 章集中说明。这样的安排既能避免理论章与实现章重复铺陈，也能让 Agent 的讨论始终贴住当前代码的真实能力边界。

\section{本章小结}
本章从多模态健康数据融合、疾病风险预测与情景推演，以及 OCR、RAG 与 Agent 等方面，概述了后续章节所依赖的理论与技术背景。整体来看，平台以结构化临床风险为起点，结合遗传、行为相关状态和文档证据形成综合风险表示，并在此基础上扩展到情景推演和受控问答。上述内容为第 4 章的算法设计和第 5 章的系统实现提供了统一的概念支撑。
