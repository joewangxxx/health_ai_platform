\chapter{相关理论与关键技术}
\label{sec:theory}

本章围绕本文后续研究所依赖的最小理论背景展开，重点说明多模态健康数据融合、疾病风险预测与情景推演，以及 OCR、RAG 与 Agent 问答等关键技术的基本思想。与第 4 章的算法设计和第 5 章的系统实现不同，本章不再展开过细的工程细节、部署机制或测试方法，而是为后文的方法建模与系统落地提供统一概念基础。

\section{多模态健康数据融合基础}
\subsection{健康数据的多源异构性}
健康管理场景中的数据通常具有明显的异构特征。临床指标反映个体在当前时间点的体征与检验状态，基因数据描述较稳定的遗传易感性，行为与 IoT 数据则体现短时变化的生活方式和生理波动。三类数据在时间尺度、观测粒度和噪声特性上均不相同，因此单一数据源往往难以完整刻画个体风险水平。本文平台正是在这一背景下，将结构化画像、体检报告解析结果、基因信息和行为观测组织为互补证据，用于构建更适合主动健康管理的综合风险表示。

\subsection{风险融合的基本思想}
在平台的工程实现中，临床风险评估结果作为基础先验，遗传与行为信息作为修正因子参与综合风险计算。其核心思想可以概括为
\begin{equation}
    P_{\mathrm{fusion}}=\operatorname{clip}(P_c\cdot \alpha \cdot \beta,\;0.1,\;99.9),
    \label{eq:fusion_theory_compact}
\end{equation}
其中 \(P_c\) 表示基于结构化健康指标得到的临床风险先验，\(\alpha\) 表示遗传风险修正因子，\(\beta\) 表示行为风险修正因子。需要说明的是，上式更适合作为受贝叶斯思想启发的工程化融合表达，而非严格意义上的概率图模型后验推断。与之对应的代码实现位于 \texttt{backend/services/fusion\_service.py} 的 \texttt{calculate\_composite\_risk()} 中，其作用是将不同证据源组织为统一的综合风险输出。

除静态融合外，平台还允许将实时心率等短时信号作为事件触发信息，对当前风险快照进行有限度更新。这种机制使融合结果不仅能够描述“当前风险水平”，也能够对短时异常状态作出反馈，但其本质仍是基于规则的工程更新，而不是连续时间医学状态空间估计。

\section{疾病风险预测与情景推演基础}
\subsection{结构化健康风险预测}
疾病风险预测是本文平台的基础分析能力。对于结构化健康数据，集成学习模型能够较好处理非线性特征关系、缺失值和类别不均衡问题，因此本文采用 LightGBM 作为临床风险预测的主要建模工具。训练脚本 \texttt{ai\_core/train\_risk\_models.py} 对不同目标病种分别构建二分类模型，并通过分层抽样与泄漏特征剔除机制，避免将与诊断定义高度重叠的变量直接带入模型，从而提高风险评估结果的可信度。

在此基础上，遗传风险评分用于补充长期易感性信息，行为风险模型和营养视觉模型则用于提供辅助修正证据。它们在系统中的角色并非独立终判，而是帮助平台在临床主风险之外吸收更多维度的信息。因此，从论文主线看，本节的重点是“如何形成稳定的临床主风险输入”，而不是对每一个辅助模型分别展开完整算法论证。

\subsection{面向干预的情景推演}
健康管理平台不仅需要识别当前风险，还需要支持对未来风险变化的辅助分析。基于这一需求，本文在风险评估基础上引入情景推演思路：一方面模拟年龄增长、体重变化、血压和血糖波动对未来风险的影响，另一方面评估生活方式调整后风险可能出现的变化方向。其核心目标不是给出严格的临床因果结论，而是提供可比较的风险差异，用于辅助用户理解不同干预方案的潜在收益。

对应到实现层，\texttt{backend/services/projection\_service.py} 通过复用融合风险引擎，对“当前状态”和“调整后状态”分别计算风险结果，并输出风险变化幅度。由此可见，本文所谓的“反事实”或“干预推演”，更适合理解为基于规则扰动与同一风险引擎复算的情景分析机制，而不是完整的结构因果模型求解。

\section{OCR、RAG与Agent关键技术}
\subsection{OCR与知识增强问答}
在真实健康管理场景中，用户提供的信息并不总是完全结构化。体检报告、检验单和其他医疗文档通常以 PDF 或图像形式存在，因此需要先通过 OCR 将关键信息提取为可计算字段，再与用户画像共同进入后续分析链路。本文平台中的 OCR 服务由 \texttt{backend/services/ocr\_service.py} 实现，核心作用是把半结构化医学文档转化为后续可利用的结构化摘要，而不是替代人工完成完整临床解释。

对于医学知识问答，平台采用检索增强生成思路。其基本过程是：先从知识库中检索与当前问题相关的文本证据，再将检索结果与用户画像、报告摘要等信息共同送入回答生成链路。对应实现位于 \texttt{backend/services/rag\_service.py}，其 \texttt{search\_context\_with\_quality()} 不仅返回检索文本，也返回检索状态和质量摘要。这说明平台中的 RAG 不只是简单的“向量检索 + 文本拼接”，而是带有证据质量约束的知识增强问答支撑机制。

\subsection{面向医疗场景的Agent基本机制}
与通用开放式问答不同，医疗健康场景对回答边界、风险提示和工具使用约束更加敏感。基于这一特点，本文平台中的 Agent 不采用完全开放的自由生成方式，而是在回答前增加安全分流、工具约束和证据充分性判断等步骤。相关能力主要由 \texttt{backend/services/agent\_safety.py}、\texttt{backend/services/chat\_service.py} 和 \texttt{backend/services/agent\_tools.py} 协同实现，其基本流程包括：先判断问题所属风险车道，再限定可用工具集合，随后结合画像、检索证据和工具输出判断当前证据是否足以支持回答，最后生成受约束的回复结果。

需要强调的是，本章仅讨论 Agent 的基本技术思想与医疗场景适配性，不在此处展开完整的运行链和治理细节。相关实现将在第 5 章集中说明。这样的安排有助于避免理论章与实现章重复铺陈，也使 Agent 在全文中既保留为亮点，又不脱离当前代码的真实能力边界。

\section{本章小结}
本章从多模态健康数据融合、疾病风险预测与情景推演，以及 OCR、RAG 与 Agent 关键技术三个方面，概述了本文后续研究所依赖的基础理论与技术背景。总体而言，平台以结构化临床风险为基础，结合遗传、行为和文档证据形成综合风险表示，并在此基础上扩展到受控问答与干预推演。上述内容为第 4 章的关键算法设计和第 5 章的系统实现提供了统一的概念支撑。
